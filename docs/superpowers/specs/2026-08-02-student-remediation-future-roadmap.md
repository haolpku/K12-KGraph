# 学生错题补弱系统：未来规划

- 日期：2026-08-02
- 状态：规划候选，不属于当前 Demo
- 当前基线：[功能型 Demo 设计](./2026-08-02-student-mistake-diagnosis-remediation-design.md)

## 1. 文档目的

本文件集中记录为了降低 Demo 复杂度而暂缓的生产化能力。这些需求没有取消，但不进入当前 Demo 的实现计划和验收范围。

未来每个阶段单独立项、重新确认需求并编写实施计划，不因出现在本文件中而自动获得实施授权。

## 2. 阶段一：权限与数据治理

### 2.1 目标

允许系统使用真实学生数据，并把学生、教师、管理员和服务账号的访问边界落实到平台与业务层。

### 2.2 候选能力

- 飞书 Base 高级权限和角色体系；
- 学生记录级隔离；
- 教师只能访问绑定学生；
- 只读教师、可编辑教师和管理员角色；
- 敏感字段的字段级权限；
- 图片附件的查看、下载和转发限制；
- 服务账号最小权限与凭据轮换；
- 学生数据脱敏；
- 数据保存期限、归档和删除机制；
- 教师修改、状态变化和系统操作的完整审计；
- 导出限制和批量下载控制；
- 使用真实学生数据前的隐私、合规与安全评审。

### 2.3 进入条件

以下任一条件出现时，应优先启动本阶段：

- 使用真实学生数据；
- 多名非受控演示人员访问 Base；
- 多个教师只能查看各自班级；
- 进入学校或机构试点；
- 需要导出、共享或长期保存学生附件。

## 3. 阶段二：可靠性与生产运行

### 3.1 目标

让长流程在模型、网络、Base 或服务异常时能够恢复，并具备可观察、可运维和可控成本。

### 3.2 候选能力

- Deep Agents checkpoint；
- 持久化任务队列；
- Base 写入重放、幂等操作表和冲突处理；
- 指数退避和分级重试；
- 备用模型和模型能力降级；
- 完整案例状态机与断点恢复；
- 失败任务人工处理队列；
- 结构化日志、指标、链路追踪和告警；
- 模型调用成本、延迟和成功率统计；
- 限流、并发控制、熔断和压力测试；
- 数据备份与恢复演练；
- Base Repository 接口后的独立业务数据库迁移方案。

### 3.3 进入条件

- Demo 之外需要持续运行；
- 同时服务多个学生；
- 一次失败不能依靠人工重新演示；
- 需要明确的可用性、延迟或恢复目标；
- Base 容量、并发或查询能力成为瓶颈。

## 4. 阶段三：完整学习闭环

### 4.1 目标

从“能够演示一次补弱”升级为“能够持续、可验证地提升学生掌握水平”。

### 4.2 数据模型升级

将 Demo 的四张表扩展为七张规范化业务表：

1. `StudentProfile`；
2. `MistakeCase`；
3. `DiagnosisResult`；
4. `RemediationPlan`；
5. `LearningAttempt`；
6. `MasteryRecord`；
7. `TeacherReview`。

从 `MistakeCase` 中拆出诊断、补弱计划和教师复核，保留版本和历史记录。

### 4.3 候选能力

- 题库优先的标准答案与双模型独立复核；
- 多候选错因和 Top-1/Top-3 诊断评估；
- 1–3 道动态验证题；
- 使用教师黄金案例集进行置信度校准；
- 未知、疑似薄弱、补弱中、初步掌握、稳定掌握五级状态；
- 不同题型、提示层级和迁移题的证据权重；
- 按年级配置每日时长或题量预算；
- 跨会话继续；
- 1–3 天间隔复测；
- 自动提醒；
- 教师机器人复核卡；
- 教师结果实时回传学生；
- 连续多个学习会话无改善时自动升级教师；
- 未见迁移题和间隔保持作为学习效果指标。

### 4.4 进入条件

- 需要运行超过一次演示会话；
- 需要证明长期学习效果；
- 教师需要结构化复核和历史追踪；
- 有足够教师标注数据校准诊断和置信度。

## 5. 阶段四：规模化产品能力

### 5.1 目标

支持学校组织、多班级、多学科和持续运营。

### 5.2 候选能力

- 学籍、教务或花名册同步；
- 学校、年级、班级和教师组织关系；
- 教师班级看板；
- 学生学习趋势和干预效果分析；
- 管理员运营视图；
- 批量任务和班级练习；
- 多学科知识图谱、题型和提示策略；
- 题库版本、质量审核和去重；
- 知识图谱治理工作流；
- A/B 测试和正式学习效果评估；
- 多班级、多学校试点；
- 成本预算和容量规划。

### 5.3 进入条件

- 单班或小范围试点指标稳定；
- 有明确的学校组织接入需求；
- 小学数学闭环已经证明有效；
- 有资源维护多学科内容、题库与图谱。

## 6. 推荐实施顺序

```mermaid

    D["当前：功能型 Demo"] --> P1["阶段一：权限与治理"]
```

如果系统开始使用真实学生数据，阶段一必须优先于其他扩展。阶段二和阶段三可以在明确边界后交错推进，但不能在缺少基本权限与治理的情况下进入真实学校试点。

## 7. Demo 兼容性要求

当前 Demo 只保留少量不会明显增加复杂度、但能降低未来迁移成本的稳定边界：

- `student_id`、`case_id`、`attempt_id` 使用稳定唯一 ID；
- Base 中保存 Neo4j 的稳定 Concept / Skill ID，不复制图谱关系；
- Agent 使用结构化输入输出；
- 业务服务通过清晰的数据访问边界读写 Base；
- `MistakeCase` 中合并字段命名与未来拆表字段保持一致；
- 图片保留与原始消息和案例的关联。

除此之外，不为未来能力提前建设框架、权限层、队列或复杂抽象。

## 8. 非承诺说明

本规划描述可能的演进方向，不承诺具体日期、技术选型或实施顺序。每个阶段开始前都需要重新完成需求确认、设计审批、成本评估和验收定义。
